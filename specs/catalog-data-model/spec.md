# SPEC-012 — Catalogue Data Model and Conventions

**Status:** draft
**Owner:** Artem Zhuravlev
**Last updated:** 2026-10-15
**Refines:** SPEC-001 section 8, 16 · SPEC-005 · SPEC-008

## Platform facts (verified in `core/upload/`)

1. Core entities and tables: `product` (+ `_description`, `_to_category`, `_image`, `_option`,
   `_option_value`, `_attribute`, `_discount`, `_special`, `_related`, `_filter`, `_reward`,
   `_recurring`, `_to_store`, `_to_layout`, `_to_download`), `category` (+ `_description`, `_path`
   closure table, `_filter`, `_to_store`, `_to_layout`), `manufacturer`, `attribute` /
   `attribute_group`, `option` / `option_value`, `filter` / `filter_group`, `information`,
   `download`, `review`.
2. ocStore-specific columns: `oc_product.noindex`, `oc_category.noindex` (default 1!),
   `oc_product_description.meta_h1`; blog tables `article*`, `blog_category*`.
3. `oc_product`: `model varchar(64)` (required SKU-like), `sku`, `upc/ean/jan/isbn/mpn`, `quantity`,
   `stock_status_id`, `image`, `manufacturer_id`, `shipping`, `price decimal(15,4)`, `tax_class_id`,
   `date_available`, `weight/length/width/height` + class ids, `subtract`, `minimum`, `sort_order`,
   `status` (default **0**), `viewed`.
4. Catalog model API: `catalog/model/catalog/product.php` — `getProduct`, `getProducts($data)` with
   filters `filter_category_id|filter_sub_category|filter_filter|filter_name|filter_tag|
   filter_description|filter_manufacturer_id|filter_id` + sort/start/limit, `getProductSpecials`,
   `getLatest/Popular/BestSellerProducts`, attributes/options/discounts/images/related, totals.
5. Category tree uses `oc_category_path(category_id, path_id, level)` maintained by the admin model on
   add/edit/move; direct SQL edits break navigation.
6. Product images: path relative to `DIR_IMAGE` (`catalog/...`); thumbnails generated on demand into
   `image/cache/` by `catalog/model/tool/image->resize($file,$w,$h)`.
7. Prices: stored base-currency decimals; displayed through `currency->format(tax->calculate(...))`.

## Problem

Catalogue data (products, categories, attributes, options, filters) is runtime data created in
admin, outside git — yet the shape of that data (which attributes exist, how options are used, naming,
image rules) is an architectural decision that templates, import tools, search and SEO depend on.

## Purpose

Define the conventions that make catalogue data consistent and machine-processable, the
reference-data seeds that live in git, the rules for custom catalogue fields and the import/export
contract.

## Scope

Reference data in git, naming conventions, custom fields on products (without altering core
tables), image conventions, import/export format, catalogue-related settings, derived data.

## Out of scope

Concrete categories/products of the shop, pricing policy, supplier feeds (own specs).

## Functional requirements

### Reference data in git

- **REQ-CAT-001** — Data that is part of the *store design* rather than daily content is stored as JSON
  in `custom/catalog/reference/` and applied by idempotent migrations: tax classes + rates + rules,
  geo zones and zone mappings, length/weight classes, stock statuses, customer groups, attribute
  **groups**, option **definitions** (type, name per language), filter groups, information pages
  with fixed meaning (terms, privacy, delivery — key by `seo keyword` and a registry
  `custom/catalog/reference/information.json` that maps meaning -> `information_id`).
- **REQ-CAT-002** — Entities receive stable **codes** for programmatic reference. Because core tables have no
  code column, the mapping lives in `oc_ocs_catalog_code (entity_type, entity_id, code)` with a
  unique index `(entity_type, code)`; helpers `Ocs\Catalog\Code::id('attribute_group','specs')`.
  Migrations create reference entities through the **core admin models** (so `category_path`,
  descriptions, store links stay correct): the migration helper `$m->catalog->ensureCategory($code,
  $data)` loads `admin/model/catalog/category.php` through a minimal admin bootstrap, never raw
  SQL into category tables.
- **REQ-CAT-003** — Demo catalogue for development (`custom/db/seed/…`) is generated by a seed
  script from `custom/catalog/demo/*.json` through the same admin models; never used in production.

### Naming and content conventions

- **REQ-CAT-010** — Product `model` is the unique business SKU (enforced by a admin model event that
  rejects duplicates; format regex configured per store in `custom/catalog/rules.json`).
- **REQ-CAT-011** — Required content per language for an active product: `name`, `description`,
  `meta_title`, `meta_description`, `meta_h1` (ocStore), SEO keyword; admin form validation extended
  by an event on `admin/model/catalog/product/addProduct|editProduct/before` that returns an error
  structure core can display (or blocks `status=1` while incomplete).
- **REQ-CAT-012** — `noindex` flags: new products/categories default to indexable only after content
  completeness (REQ-CAT-011); the migration sets the column default behaviour via event, not by
  altering the core column default.
- **REQ-CAT-013** — Categories depth <= 3; names <= 60 characters; sort order multiples of 10.
- **REQ-CAT-014** — Attributes hold facts shown in specs tables; Options hold purchasable variations
  (size/colour). Mixed use is forbidden; filters (`oc_filter`) are used only for facets listed in
  `custom/catalog/rules.json` -> `facets`.
- **REQ-CAT-015** — Manufacturer is mandatory for products (rule in REQ-CAT-011 set).

### Custom product fields

- **REQ-CAT-020** — Extra product data (e.g. `warranty_months`, `badge`, `gtin` beyond core) lives in
  `oc_ocs_product_ext (product_id PK, …)` (1:1) or `oc_ocs_product_ext_attr (product_id, key, language_id,
  value)` (EAV for sparse language-specific data). Core tables unchanged (REQ-ARCH-053).
- **REQ-CAT-021** — Admin UI for them: an OCMOD-free approach — events on `admin/view/catalog/product_form/before`
  (inject HTML tab) + `admin/model/catalog/product/addProduct|editProduct/after` (persist) +
  `deleteProduct/after` (cleanup). Storefront data injected via `catalog/view/product/product/before`.
- **REQ-CAT-022** — Copying a product (`copyProduct`) copies the extension rows (event on `copyProduct/after`).

### Images

- **REQ-CAT-030** — Images stored under `image/catalog/<entity>/<yyyy>/<mm>/<slug>-<n>.<ext>`; names lowercase
  Latin, no spaces; formats jpg/png/webp; max upload 5 MB (`config_file_max_size`); main image >= 1000 px
  on the long side. Size roles per theme (SPEC-006 REQ-THM-030) must be derivable from the main image.
- **REQ-CAT-031** — `image/cache` is disposable; a tool `scripts/images-clean.mjs` removes cache files whose
  source is missing and lists orphan sources (read-only report by default).
- **REQ-CAT-032** — Alt text derives from product name + manufacturer unless the template has a
  translated override; never empty.

### Import / export

- **REQ-CAT-040** — Bulk catalogue changes use one format: UTF-8 CSV/JSON files in `var/import/`, one row per
  product with columns defined in `custom/catalog/import-schema.json` (sku/model, per-language fields,
  category codes, manufacturer, attributes by code, options, prices, quantity, images).
- **REQ-CAT-041** — Importer is a CLI (`php scripts/catalog-import.php <file> [--dry-run]`) that calls the **admin
  models** (`addProduct/editProduct`) via a minimal bootstrap, validates against REQ-CAT-010/011, is
  idempotent by `model`, reports created/updated/skipped/errors per row, and never deletes
  products (a separate `--disable-missing` flag sets `status=0`).
- **REQ-CAT-042** — Export CLI produces the same schema for backup/diff; round-trip (export -> import) is lossless
  (test).
- **REQ-CAT-043** — Price changes go through the importer or admin only; direct SQL on `oc_product.price` is
  forbidden (lint).

### Derived data & caches

- **REQ-CAT-050** — `oc_category_path` consistency check (`scripts/catalog-doctor.php`): detects missing
  path rows, orphans, cycles, products without category/manufacturer, active products without image,
  duplicate SEO keywords; read-only unless `--fix-paths`.
- **REQ-CAT-051** — Cache keys for catalogue lookups (`ocs_catalog.*`) are invalidated by events on admin
  product/category mutations (REQ-ARCH-110).

## Non-functional requirements

- **REQ-CAT-060** — Catalogue pages stay within 25 queries per request on category/product pages beyond
  core's baseline (measured by the debug event in local).
- **REQ-CAT-061** — Import of 5 000 products completes in < 10 minutes on the reference machine.

## Data requirements

`oc_ocs_catalog_code`, `oc_ocs_product_ext`, `oc_ocs_product_ext_attr`; JSON sources under
`custom/catalog/`.

## Edge cases

- Duplicate `model` in existing data -> doctor lists; importer refuses to update ambiguous rows.
- Language added later -> importer requires per-language columns for all enabled languages or fails
  with explicit missing list.
- Category moved in admin -> core updates path rows; our caches invalidated by event.
- Deleted product with extension rows -> cleaned by event; doctor reports leftovers.
- Product with options and `subtract` -> stock per option value (core), importer supports it explicitly.

## Acceptance criteria

- [ ] Reference migration creates tax classes/geo zones/etc. idempotently.
- [ ] Importer dry-run on a fixture reports expected counts; real run creates products visible on storefront.
- [ ] Round-trip export/import test passes.
- [ ] Doctor detects a deliberately corrupted `category_path` in a fixture.
- [ ] Lint rejects raw `UPDATE oc_product SET price`.

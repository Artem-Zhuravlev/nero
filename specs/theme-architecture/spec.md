# SPEC-006 — Storefront Theme Architecture

**Status:** in-progress
**Owner:** Artem Zhuravlev
**Last updated:** 2026-10-15
**Refines:** SPEC-001 REQ-ARCH-020 · **Facts:** [`docs/ocstore-internals.md`](../../docs/ocstore-internals.md) §8, [`docs/ocstore-reference.md`](../../docs/ocstore-reference.md) §3

## Problem

The storefront look must be fully ours without forking core templates. Core resolves templates
per route with fallback to `default`, but the default header hard-codes asset paths and a Google
Fonts CDN, image sizes come from `theme_<name>_image_*` settings, and checkout/cart JS in
`common.js` depends on specific DOM ids. A theme needs rules that keep these working.

## Purpose

Define the `ocs` theme: structure, which templates may be overridden, asset pipeline, image-size
settings, JS/CSS conventions, accessibility/performance baselines, and how the theme is
registered and selected.

## Scope

`custom/theme/ocs/`, its admin theme extension `ocs` (type `theme`), theme settings, asset
loading, template override discipline, variables available to templates, the checklist for
overriding a core template.

## Out of scope

Visual design (colours, layout of concrete pages) — each page redesign is its own spec; CMS content.

## Functional requirements

### Registration and selection

- **REQ-THM-001** — Theme code `ocs`. Storefront files live in `custom/theme/ocs/`, built to
  `catalog/view/theme/ocs/`. The admin side is an extension of type `theme` whose code is exactly `ocs`, in directory
  `custom/extensions/ocs/` (documented exception to the `ocs_` prefix rule of REQ-EXT-001, because
  core derives the theme directory from the extension code), route `extension/theme/ocs`.
- **REQ-THM-002** — A migration registers it: `oc_extension('theme','ocs')`, permission grant
  `extension/theme/ocs`, settings `theme_ocs_status=1`, `theme_ocs_directory=ocs`, all
  `theme_ocs_image_*` and `theme_ocs_product_limit`, `theme_ocs_product_description_length`
  copied from the `theme_default_*` values present at migration time (reference §3 lists the
  keys), then `config_theme=ocs` (store 0).
- **REQ-THM-003** — Core fails with "A theme has not been assigned" if `theme_<theme>_status` is
  falsy; therefore the `ocs` migration sets status **before** `config_theme` and the theme
  can be reverted by setting `config_theme=default` (rollback documented in the migration).

### Template override discipline

- **REQ-THM-010** — The theme contains **only** files that differ from `default`. A byte-identical
  copy of a default template is an error (verify compares against
  `core/upload/catalog/view/theme/default/…`).
- **REQ-THM-011** — Each overridden template starts with a Twig comment
  `{# @core-file catalog/view/theme/default/template/<route>.twig @core-version 3.0.3.7 #}`
  (REQ-ARCH-101) so a core upgrade can list overrides whose base changed.
- **REQ-THM-012** — Twig variables supplied by controllers are the contract: an override may not
  rely on a variable that the controller for that route does not set (checked by reading the
  controller; extra data is provided through a `catalog/view/<route>/before` event, SPEC-007).
- **REQ-THM-013** — Required DOM hooks used by core JS (`catalog/view/javascript/common.js`,
  checkout/cart templates) are preserved: ids and classes listed in
  `custom/theme/ocs/HOOKS.md` (generated by the author of each override from the original
  template: element ids such as `#cart`, `#search`, `#button-cart`, `.btn-checkout` patterns,
  `data-toggle` attributes, form field names). Verify cannot check this automatically; it is a
  review checklist item (SPEC-009).
- **REQ-THM-014** — Language strings in templates always come from controller variables
  (`{{ text_… }}`) — no literal user-visible text in `.twig` (REQ-ARCH-034). Theme-specific
  strings use a theme language file loaded by a `view`/`controller` event, key prefix `ocs_`.
- **REQ-THM-015** — Output escaping rules of REQ-ARCH-063 apply (autoescape is off).

### Assets

- **REQ-THM-020** — `custom/theme/ocs/stylesheet/stylesheet.css` is the single entry stylesheet;
  optionally generated from SCSS (`*.scss` in the same folder) compiled by core's
  `startup/sass` **only if** `developer_sass` setting is on, otherwise precompiled CSS is committed.
  Decision recorded: **CSS is committed**, SCSS is optional dev input; build fails if a `.scss`
  is newer than its `.css` in the repo (checked by content hash header in the CSS).
- **REQ-THM-021** — Our overridden `common/header.twig` links: jQuery and Bootstrap as in
  default (same files from `catalog/view/javascript/`), Font Awesome, the theme stylesheet with
  `?v={{ asset_version }}` (REQ-ARCH-114), then the dynamic `styles`/`scripts`/`links`/`analytics`
  loops unchanged. No third-party CDN at runtime (self-hosted fonts in
  `custom/theme/ocs/fonts/`, `font-display: swap`).
- **REQ-THM-022** — `asset_version` variable is injected by a `catalog/view/common/header/before`
  event handler from `BUILD_INFO.json` (`gitCommit` short, or `treeHash` first 8 chars).
- **REQ-THM-023** — JS: no new frameworks. Theme JS in `catalog/view/theme/ocs/javascript/theme.js`
  (ES5-compatible or transpile-free ES2017 where core's jQuery 2.1.1 pages already assume
  modern browsers), loaded after `common.js`, namespaced `window.OCS`, no globals otherwise.
- **REQ-THM-024** — Images in the theme: `custom/theme/ocs/image/` -> `…/ocs/image/`; formats
  svg/png/webp; every image has a documented purpose in `ASSETS.md`.

### Image sizes (settings)

- **REQ-THM-030** — Image dimension settings `theme_ocs_image_<role>_(width|height)` exist for all
  roles of the default theme (`thumb, popup, category, manufacturer, product, additional,
  related, compare, wishlist, cart, location`). Templates and CSS use the **same** numbers: a
  design spec defines the sizes, a migration sets them, CSS aspect-ratios reference them in
  comments.
- **REQ-THM-031** — Pagination size `theme_ocs_product_limit` and description length are set by
  migration, never in templates.

### Responsiveness, accessibility, performance baselines

- **REQ-THM-040** — Mobile-first; tested at 360, 768, 1280 px widths; no horizontal scroll.
- **REQ-THM-041** — Accessibility: semantic landmarks (`header nav main footer`), one `h1` per
  page, `alt` on content images, visible focus, contrast >= 4.5:1 for text, form labels bound to
  inputs, buttons are `<button>`.
- **REQ-THM-042** — Performance: LCP image has explicit width/height, other images
  `loading="lazy"`; total theme CSS <= 150 KB unminified, theme JS <= 60 KB; no render-blocking
  third-party requests.
- **REQ-THM-043** — SEO markup: structured data (`schema.org` Product, BreadcrumbList) emitted
  from templates using controller-provided data; canonical via `document->addLink`.

### Scope control

- **REQ-THM-050** — The first iteration overrides at most: `common/header`, `common/menu`, `product/product`,
  `product/category`, `checkout/*` as required by its own design spec. `common/footer` and `common/home`
  are styled by CSS only (no markup change needed, REQ-THM-010). `product/thumb` does not exist in ocStore
  3.0.3.7: the product card is inlined in each listing template (category, search, special, manufacturer_info,
  modules featured/latest/bestseller/special, blog); the remaining listings are overridden in a later iteration
  and until then are styled by CSS only. Every further template needs an item in the
  design spec.
- **REQ-THM-051** — Checkout templates are overridden last and only visually (markup of forms and
  JS ids preserved), because order flow correctness is owned by core.

## Non-functional requirements

- **REQ-THM-060** — Theme build adds no runtime dependency; no Node tooling is needed to deploy
  (CSS committed).
- **REQ-THM-061** — Theme can be disabled by `config_theme=default` with no data loss.

## Data requirements

Settings only (`theme_ocs_*`, `config_theme`).

## Edge cases

- Template exists both as DB override (admin Theme Editor, `oc_theme`) and file -> DB override
  wins (core behaviour). The Theme Editor is treated as forbidden in non-local environments
  (permission removed from non-admin groups by migration); documented in the playbook.
- Module twig inside `extension/module/*.twig` is looked up in the theme first, then default.
- Multi-store: each store may set a different `config_theme`; the `ocs` theme settings are per
  store id (migration writes store 0 only).
- OCMOD-patched templates are served from `DIR_MODIFICATION` before theme files in some paths
  (core `event/theme.php` checks `is_file(DIR_MODIFICATION …)`) -> OCMOD on theme templates is
  forbidden (REQ-OCM-040).

## Acceptance criteria

- [ ] With only an overridden `common/header.twig`, every page renders and uses our header.
- [ ] Switching `config_theme` to `default` and back works without errors.
- [ ] No byte-identical copies; every override has `@core-file` header.
- [ ] Lighthouse (manual) accessibility >= 90, performance >= 80 on home in a desktop profile.

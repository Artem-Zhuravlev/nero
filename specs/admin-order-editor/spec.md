# SPEC-122 — Админка: редактор заказа на одной странице

**Status:** implemented
**Owner:** Zhuravlev Artem
**Last updated:** 2026-10-29

## Problem

Форма создания/редактирования заказа в админке (core `sale/order_form`) — это 5 вкладок («Клиент», «Товары», «Адрес плательщика», «Адрес доставки», «Итого»), каждая со своей кнопкой «Продолжить»/«Применить», которые надо нажимать по порядку (~15 AJAX-вызовов к API каталога). Адрес плательщика и адрес доставки заполняются дважды одними и теми же данными. Менеджер ходит по вкладкам туда-сюда, забытая кнопка — потерянные данные или ошибка при сохранении.

## Purpose

Один экран редактирования заказа, как в кабинете Prom.ua: все блоки видны сразу, пересчёт и синхронизация с сессией API — автоматические, адрес вводится один раз.

## Scope

- Админская форма заказа `sale/order.add` и `sale/order.edit` (замена шаблона).
- Лёгкая серверная поддержка (admin event), если нужны дополнительные переменные.
- Языковые строки uk-ua / en-gb (других языков админки в проекте нет).

## Out of scope

- Страница просмотра заказа (`sale/order.info`), список заказов, история, возвраты, счёт-фактура.
- Бизнес-логика заказа: расчёт, модули итогов, скидки — остаются ядром (API каталога, `api/order/add|edit`).
- Новые таблицы/поля БД.
- Новые способы доставки/оплаты (Новая Почта SPEC-085 работает как есть).

## Functional requirements

- **REQ-ORD-001** — Форма — одна страница без вкладок-шагов: блоки «Клиент», «Товары», «Доставка», «Оплата», «Итого и комментарий» видны одновременно; справа липкая сводка с итогами и кнопкой «Сохранить».
- **REQ-ORD-002** — Нет кнопок «Продолжить» по шагам: изменения клиента, адреса, товаров, количества, купона/ваучера/баллов автоматически (с debounce) синхронизируются с сессией API и пересчитывают способы доставки/оплаты и итоги.
- **REQ-ORD-003** — Адрес вводится один раз: блок «Доставка» содержит адрес; флажок «Адрес плательщика совпадает с адресом доставки» включён по умолчанию, при выключении появляется отдельная форма плательщика (предзаполнена копией). При включённом флажке плательщик отправляется в API копией доставки.
- **REQ-ORD-004** — Клиент: автоподбор существующего клиента подставляет имя, телефон, email, группу и адреса (выбор из адресной книги в блоке доставки); можно оформить заказ гостем без выбора клиента.
- **REQ-ORD-005** — Товары: поиск с автоподбором, опции товара, количество через степпер, удаление, цена и сумма строки видны сразу; ваучеры — сворачиваемым блоком.
- **REQ-ORD-006** — Способы доставки и оплаты — радио-карточки, загружаемые автоматически после заполнения адреса/товаров; выбор по умолчанию, если вариант один или ранее выбранный ещё доступен (при редактировании сохраняется выбранный).
- **REQ-ORD-007** — Итого: строки итогов (подытог, доставка, налоги, купон, итог) обновляются после каждого изменения; индикатор «Пересчёт…» блокирует «Сохранить», пока идёт синхронизация.
- **REQ-ORD-008** — Валидация: ошибки API подсвечиваются у конкретных полей и дублируются сводкой вверху; «Сохранить» прокручивает к первой ошибке; введённые данные не теряются.
- **REQ-ORD-009** — Сохранение: `api/order/add` / `api/order/edit` вызывается один раз с итоговым состоянием; после успеха — сообщение и переход к заказу; повторный клик во время запроса игнорируется.
- **REQ-ORD-010** — Редактирование существующего заказа: форма открывается заполненной (клиент, товары, адреса, способы, купон), сессия API инициализируется автоматически.
- **REQ-ORD-011** — Смена магазина или валюты безопасно пересоздаёт сессию корзины, с предупреждением если в корзине есть товары.
- **REQ-ORD-012** — Пользовательские поля (custom fields) клиента и адресов отображаются и валидируются.

## Non-functional requirements

- **REQ-ORD-020** — Адаптивно: на телефоне блоки в одну колонку, сводка внизу с липкой кнопкой «Сохранить».
- **REQ-ORD-021** — Без правки `core/`: подмена шаблона через admin view event; контроллер, модель и API ядра не меняются; при отключённом расширении работает штатная форма.
- **REQ-ORD-022** — Нет гонок: запросы к API сериализуются в очередь, устаревшие ответы отбрасываются; нет циклов пересчёта.
- **REQ-ORD-023** — Стиль админки (Bootstrap 3) сохранён; свои CSS/JS подключаются только на этой странице.

## Data requirements

Нет изменений схемы. Событие регистрируется идемпотентной миграцией расширения.

## Interfaces

- Admin event `admin/view/sale/order_form/before` — подмена шаблона на `extension/ocs_order_editor/order_form`.
- Эндпоинты API каталога без изменений: `api/customer`, `api/cart/*`, `api/payment/*`, `api/shipping/*`, `api/coupon`, `api/voucher`, `api/reward`, `api/order/add|edit`.

## Edge cases

- Товара нет в наличии / минимум количества -> предупреждение из API у строки; заказ можно сохранить, как в ядре.
- Нет доступных способов доставки -> сообщение и подсказка проверить адрес/товары, «Сохранить» заблокирована.
- Сессия API истекла или API выключен -> понятное сообщение сверху с просьбой обновить страницу (новый токен выдаёт только серверная страница); введённые данные при этом не отправляются.
- Клиент снят после выбора -> адреса из адресной книги сбрасываются, введённые вручную остаются.
- Флажок «совпадает» включён, адрес доставки меняется -> плательщик обновляется автоматически.

## Acceptance criteria

- [ ] Новый заказ создаётся без переключения вкладок и без промежуточных кнопок.
- [ ] Адрес вводится один раз; заказ сохраняется с одинаковыми payment_* и shipping_* полями.
- [ ] Редактирование существующего заказа открывается заполненным и сохраняет изменения (товар, количество, адрес, доставка).
- [ ] Ошибки валидации видны у полей, данные не теряются.
- [ ] `npm run verify` зелёный, архив темы пересобран (`npm run pack:theme`).
